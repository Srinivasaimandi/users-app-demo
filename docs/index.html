Users App — Developer Guide

How the demo users service is built, what each API does, and what to watch for when you change it.

Node.js 24Express 4Apollo Server 3 Port 9899JSON file storageNo build step

Overview

The Users App is a small user-management service. Its purpose is to be a stable target for automated tests in other repositories, so it exposes the same data through three surfaces:

  • REST API under /api, documented live with Swagger UI at /api-docs/.
  • GraphQL API at /graphql, with the Apollo explorer on the same URL.
  • Web UI: a login page (/) and a users table (/usersPage.html) built with plain HTML, Bootstrap and vanilla JavaScript.

There is no database. Users live in a JSON file that is read and rewritten on every request, and can be reset to a known seed at any time. That makes test runs repeatable.

Running it

Locally

npm install
npm start          # node index.js → http://localhost:9899

There is no dev or watch script. nodemon is a dev dependency, so npx nodemon index.js gives you restart-on-save. Note that a restart clears every login key (see Authentication).

With Docker

docker build -t users-app-demo .
docker run -p 9899:9899 users-app-demo

Request flow

The order of middleware in index.js matters. Requests pass through it top to bottom:

A few details that follow from this order:

  • Static files win. express.static runs before everything else and serves / from public/index.html. A route for a path that matches a file in public/ will never be reached.
  • Every response after the static step is labelled JSON, except paths starting with /api-docs.
  • The protected routes, the 404 handler and the error handler are registered inside startApolloServer(), after await server.start(). They must stay after applyMiddleware, or the 404 handler would swallow /graphql.
  • The error handler turns malformed JSON bodies (and anything else thrown) into {"message": …}. It only exposes the message if the error is marked expose (e.g. body-parser's 400s); otherwise it returns a generic 500.

Authentication

Everything except POST /api/login, Swagger and the static UI needs an x-api-key header. middleware/auth.js accepts two kinds of key:

KeyWhere it comes fromLifetime
Fixed automation keyHard-coded as VALID_API_KEY in middleware/auth.jsNever expires; cannot be revoked
Login keycrypto.randomUUID() returned by POST /api/login24 hours (API_KEY_TTL_MS), or until logout or a server restart

Login keys are kept in an in-memory Map of key → expiry time. Expired keys are removed lazily: when someone checks that key, and in bulk whenever a new key is added.

# 1. log in
curl -s -X POST localhost:9899/api/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"johndoe","password":"$test123#"}'
# → {"apiKey":"1f0c…"}

# 2. use the key
curl -s localhost:9899/api/users -H 'x-api-key: 1f0c…'

# 3. revoke it
curl -s -X POST localhost:9899/api/logout -H 'x-api-key: 1f0c…'   # → 204

For GraphQL, Apollo's context function calls the same isValidApiKey() and throws AuthenticationError if the key is wrong. In the explorer, add the key under Headers.

Login compares the username and password as typed against the stored values. Passwords are stored in plain text in the JSON file, and the API never returns them (User.toPublic() for REST; the GraphQL User type has no password field).

Data storage

utils/dataUtils.js handles all file access:

FunctionWhat it does
ensureDataFile()Copies data-backup.json to data.json if data.json is missing. Called at startup and by every getData().
getData()Reads and parses data.json synchronously. Returns { users: [...] }.
saveData(data)Writes the whole object back, pretty-printed.
resetData()Overwrites data.json with the backup.
  • data/data.json is git-ignored and docker-ignored. Changes made through the app never show up in your working tree, and every Docker container starts from the seed.
  • To change the seed users, edit data/data-backup.json, then reset (PUT /api/users/reset-data, the resetData mutation, or the Reset data button) or delete data.json.
  • New ids are max(existing id) + 1 (nextUserId()). Deleting the user with the highest id means the next new user reuses that id.
  • All file I/O is synchronous, so a single request's read-modify-write cannot be interleaved with another's within one process. Running more than one process against the same file is not safe.

Validation rules

All rules are in utils/userValidation.js and used by both APIs.

RuleDetail
Known fields onlypickUserUpdates() keeps only name, email, username, password. Anything else in the body (including id) is dropped. Strings are trimmed.
Required on createAll four fields must be non-blank strings → "All fields are required for each user"
Partial updateOnly fields that are present are checked; a present field cannot be blank → "<field> cannot be empty"
Email format/^[^\s@]+@[^\s@]+\.[^\s@]+$/, the same check as the UI's Add User form
Unique emailCase-insensitive. On update, the user's own email doesn't count.
Unique usernameCase-sensitive (Bob and bob can both exist)
Protected usersPROTECTED_USER_IDS = [0, 3] cannot be updated or deleted
User id in URLparseUserId() accepts digits only; "4abc" or "-1" become null and return 404

REST API

Base path /api. Request and response bodies are JSON. Errors look like {"message": "…"}; 500s also include error.

MethodPathSuccessOther responses
POST/login200 {apiKey}401 bad credentials
POST/logout204Always 204, even for an unknown key
GET/users200 array204 if there are no users
POST/users201 user400 validation
POST/users/bulk201 array400 if the body is not an array or any user fails; nothing is saved
GET/users/search?name=&email=200 array204 no match; 400 if a parameter is repeated
GET/users/count200 {count}
PUT/users/reset-data200 {message}500 if the copy fails
GET/users/:id200 user404
PUT/users/:id200 user400 validation, 403 protected, 404
DELETE/users/:id204403 protected, 404

All /users routes return 401 {"message":"Unauthorized: Invalid API Key"} without a valid key.

  • Route order: in routes/users.js, /search, /count, /reset-data and /bulk are declared before /:id. Keep new fixed paths above /:id, or they will be treated as ids.
  • Search is a case-insensitive substring match. When both name and email are given, a user must match both.
  • PUT is a partial update. Send only the fields you want to change. The password can be changed this way.
  • 204 bodies: handlers call res.status(204).json([]), but HTTP drops the body of a 204, so clients receive nothing.

The Swagger spec is built at startup by swagger-jsdoc from the @swagger comments above each route. If you change a route's behaviour, update its comment in the same file.

GraphQL API

type User { id: Int!  name: String!  email: String!  username: String! }

type Query {
  users: [User!]!
  user(id: Int!): User
  searchUsers(name: String, email: String): [User!]!
  userCount: Int!
}

type Mutation {
  createUser(name: String!, email: String!, username: String!, password: String!): User!
  bulkAddUsers(users: [NewUserInput!]!): [User!]!
  updateUser(id: Int!, name: String, email: String, username: String, password: String): User
  deleteUser(id: Int!): Boolean!
  resetData: Boolean!
}

Example:

curl -s localhost:9899/graphql \
  -H 'Content-Type: application/json' \
  -H 'x-api-key: <key>' \
  -d '{"query":"mutation { createUser(name:\"Ann\", email:\"ann@x.io\", username:\"ann\", password:\"pw\") { id } }"}'

Errors use Apollo's error classes: UserInputError for validation (code BAD_USER_INPUT), ForbiddenError for editing a protected user, AuthenticationError for a bad key. Introspection is on.

REST vs GraphQL behaviour

The two APIs share rules but not handlers. These differences are deliberate or at least long-standing, and tests in other repos may depend on them:

CaseRESTGraphQL
Bulk add with an invalid or duplicate user400; nothing savedInvalid users are skipped; the rest are saved and returned
Delete a protected user403false
Delete a missing user404false
Update a missing user404null
Update a protected user403ForbiddenError
Search or list with no results204, empty body[]
Reset fails500false

Web UI

The UI is static files in public/, with no bundler. Bootstrap 5.3 and Font Awesome 6.5 load from CDNs.

Login page — index.html + scripts/index.js

  • Posts to /api/login, stores the key in localStorage["x-api-token"], then redirects to usersPage.html.
  • Clicking the word Users in the heading cycles through the cool, warm and fresh themes. The choice is saved as localStorage["users-app-theme"] and read by the users page too. Themes are CSS custom properties scoped to body[data-theme="…"].

Users page — usersPage.html + scripts/usersPage.js

  • Loads GET /api/users on page load. Any 401 clears the stored key and returns to the login page (for example, after a server restart).
  • The admin user (id 0) is never shown. Protected users get a lock icon instead of edit and delete buttons. PROTECTED_USER_IDS is duplicated here and must match utils/userValidation.js.
  • Search filters on the client, across id, name, email and username, and also matches with spaces removed. It is disabled while a row is being edited, because re-rendering would throw away the edit.
  • Edit is inline (name, email, username). Save sends a PUT; Cancel or Esc restores the row from the cached allUsers.
  • Add and Delete use modal dialogs. Delete asks for confirmation before calling the API.
  • Refresh re-fetches; Reset data calls PUT /api/users/reset-data; Logout calls /api/logout and clears the stored key.
  • User data is always inserted with textContent, never innerHTML (see textCell()). Keep it that way to avoid XSS from stored names.

Automation scripts target the element ids (username-id, password-id, search-input, add-btn, refresh-btn, reset-btn, logout-link, users-table, add-user-*, delete-user-*, …). Treat them as a public interface and don't rename them casually.

Docker & CI

  • Dockerfile: node:24, npm ci --omit=dev (so nodemon is not installed), copies the source, exposes 9899, runs node index.js. data/data.json is excluded, so each container starts from the seed.
  • GitHub Actions (.github/workflows/docker-publish.yml): on every push to main, builds a multi-arch image (linux/amd64, linux/arm64) and pushes <DOCKER_USERNAME>/users-app-demo:latest. It needs the DOCKER_USERNAME and DOCKER_TOKEN repository secrets. There is no test step.
  • Known hosts listed as Swagger servers in swagger.js: localhost, raspberrypi.local:9899, and a Render deployment. The first server entry is the relative /api, so “Try it out” always calls the server you're viewing.
  • The port is hard-coded (PORT = 9899 in index.js); it does not read process.env.PORT.

Making changes

Adding a user field

  1. Add it to USER_FIELDS in utils/userValidation.js. Every field in that list is required on create.
  2. Add it to the User constructor in models/User.js and to the object built in createUser / bulkAddUsers in controllers/userController.js.
  3. Add it to the GraphQL User type, NewUserInput, and the createUser / updateUser arguments in graphql.js.
  4. Add it to the seed users in data/data-backup.json. Existing users aren't re-validated, so without this they simply won't have the field.
  5. Update the @swagger comments in routes/users.js and, if needed, the table, the Add User form and the inline edit in public/.

Adding a REST endpoint

  1. Write the handler in controllers/userController.js. Wrap the response in User.toPublic() so passwords never leak.
  2. Register it in routes/users.js above /:id if it's a fixed path, with a @swagger block.
  3. If GraphQL should have it too, add it to graphql.js; there is no shared service layer.

Changing protected users

Update PROTECTED_USER_IDS in both utils/userValidation.js and public/scripts/usersPage.js, plus the 403 descriptions in routes/users.js and the README.

Testing

There is no automated test suite (npm test just exits with an error). Check changes by hand through Swagger, the GraphQL explorer and the UI, and reset the data afterwards.

Known issues

Found while reading the code for this guide. None of them have been fixed.

  • Three theme stylesheets are unused. bold.css, dark.css and pastel.css are in public/styles/themes/ but no page links them and the theme cycle only includes cool, warm and fresh.
  • The fixed API key is in source control. Anyone who can read the repository can call every endpoint with it. That is intended for automation, but the key should not be reused anywhere it matters.
  • Passwords are stored in plain text in data.json. Fine for a demo; don't put real credentials in it.
  • Login keys don't survive a restart, and running more than one instance means a key issued by one instance is rejected by the others.
